# ולידציית ML למדיניות מחיקה

מטרת הוולידציה היא לאמוד סיכון למחיקת אלבום שונה, ולא רק דיוק של ציון דמיון. ציון בטווח `0-100` אינו הסתברות מכוילת, גם כשהוא קרוב ל-100.

## מדיניות קיימת ומקורות אמת

הספים ומשקלי הניקוד מוגדרים ב-[config.py](../music_dup_lib/config.py), השילוב ב-[scoring_service.py](../music_dup_lib/services/scoring_service.py), והמלצות הקבוצה ב-[recommendation_service.py](../music_dup_lib/services/recommendation_service.py). מדיניות מחיקה דורשת גם keeper ברור וקשרים בטוחים אליו; אין להסיק הרשאת מחיקה מציון ML בודד.

כללי הבטיחות נמצאים ב-[ARCHITECTURE.md](ARCHITECTURE.md). שינוי סף דורש ראיות חדשות ובדיקת כל תהליך ההחלטה, כולל scoring, קיבוץ ובחירת keeper.

## ממצא היסטורי ומגבלותיו

הבדיקה הראשונית שתועדה בעבר בחנה את `ml_score` לבדו מול `similarity_model/data/album_pair_features_test.csv` באמצעות `similarity_model/models/lgbm_regressor_model.joblib`. התוויות החיוביות היו `combined_high_certainty` ו-`gemini_cached`.

| סף ML | זוגות שנבחרו | Precision | False positives |
| --- | ---: | ---: | ---: |
| >= 90 | 221 | 98.19% | 4 |
| >= 95 | 170 | 98.82% | 2 |
| >= 97 | 100 | 99.00% | 1 |
| >= 98 | 16 | 100.00% | 0 |
| >= 99 | 2 | 100.00% | 0 |

אלה תוצאות היסטוריות, שלא הורצו מחדש במסגרת עריכת התיעוד. לא נשמרו כאן תאריך ריצה, גרסת dataset או hash של המודל, ולכן אין להשתמש בהן כאישור למודל או לסף הנוכחיים. `>= 98` היה הסף הראשון ללא false positives במדגם זה בלבד; 16 זוגות אינם הוכחה למחיקה בטוחה.

הבדיקה הקודמת הצביעה על מגבלות שיש לבדוק מחדש לפני שימוש במדדים:

- חלק מה-labels נוצרו מיוריסטיקות או Gemini ולא מבדיקה אנושית עצמאית
- פיצול אקראי לפי זוגות עלול לכלול אותו אלבום גם באימון וגם בבדיקה ולנפח מדדים
- חישוב blend בבניית הנתונים היה שונה מזה שבמוצר; יש להשוות את המימושים לפני הערכה. המקור הוא [data_preparation.py](../../similarity_model/src/data_preparation.py)
- נמצא מקרה שלילי או גבולי גם מעל 97; אין לקבע מדיניות על בסיס ML לבדו

## דרישות לוולידציה שניתן להסתמך עליה

1. בנה סט אנושי עצמאי עם הבחנה בין `safe_delete`, `same_album_but_review` ו-`different`. כלול מהדורות שונות, אי התאמות בשירים, ומקרים של ניקוד אלגוריתמי נמוך לצד ML גבוה
2. הפרד train/test לפי משפחת אלבום, בלי חפיפת אלבומים דרך זוגות שונים. אין להשתמש בתוויות שנוצרו בידי אותו מודל כהוכחה עצמאית לדיוקו
3. מדוד `ml_score`, `base_score` ו-`final_score`, וגם את החלטת הקבוצה בפועל. לכל סף דווח גודל מדגם, precision, recall ו-false positives
4. דווח רווח סמך ל-precision, למשל Wilson או Clopper-Pearson. אפס טעויות במדגם קטן אינו אפס סיכון
5. בדוק את כללי הבטיחות הדטרמיניסטיים: מספר שירים, התאמת רשימת שירים, keeper וכיסוי חברי הקבוצה. Gemini משמש תמיכה; full hash יכול לתמוך בבדיקה אך אינו מחליף מדיניות החלטה

תוצאת ולידציה שנשמרת לטווח ארוך צריכה לכלול תאריך, גרסאות או hashes של המודל וה-dataset, גרסת הקוד, הגדרת התוויות, שיטת הפיצול ופקודת שחזור. כאן שומרים רק מסקנה, מגבלות והפניה לראיות; אין לצבור דוח מלא לכל ריצה.
